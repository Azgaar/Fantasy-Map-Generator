Style Editor Look and Feel

The outcome of three prototyping rounds on the Style tab, written as the specification to implement. It keeps today's structure and logic — preset, element, group, the schema's own sections — and changes how it looks and how a value is edited, reset and found.

Verdict

Build the classic layout with section cards, per-value reset, an elements dialog and a presets dialog. Nothing about which store node a control writes, or when a layer redraws, changes. The schema-driven form (SchemaForm, stylesSchema, styleMeta) stays the source of every row.

Four ideas were validated and are in scope: reset to preset section cards with live previews elements tree dialog preset screenshots dialog. Everything else that was tried is out of scope — see §2 for what and why.

The reference implementation is prototype variant A (?variant=A on a dev build): src/controllers/style-editor/prototype/variant-a-classic.ts and shared.ts. It runs on the real store through the engine seam in style-editor/index.ts, so its behaviour is the behaviour to ship; its code is throwaway and is to be rewritten, not promoted.

What prototyping settled

Three rounds, fifteen variants, all driving the live store. The first round explored structure (tree pane, concern tabs, preset-first, pick-from-map, a matrix); the second kept the panel width and varied organisation and inputs; the third converged.

The Style tab

Same panel, same order of rows, same width. The mock below is the target rendering of Labels › capital after the user changed its opacity; callouts name the parts specified in the following sections.

Layout rules

  • Panel width stays 330px (30em at the panel's 11px). No variant is allowed to widen the Menu.
  • Row order inside the tab: preset, element, group, changes line, cards. The hidden-layer banner ("Labels layer is hidden · Turn on") stays above the cards, as today.
  • Label column 8em, control column fills; a row is at least 1.9em tall so sliders, selects and colour inputs align.
  • Selects and text inputs are 1.7em tall; number inputs keep their current width. Every control keeps its current widget — slider-input, colour input, the custom font/filter/transform controls.

Rows and inputs

Reset to preset

Every leaf row and every section gate compares the store value at its path with the value the current preset holds at the same path (see §7 for the baseline). When they differ the row is changed:

  • A 3px vertical bar, colour #c0392b, at the row's left edge (outside the label, inside the card padding).
  • A ↺ button at the end of the control, colour #7a2e2e, borderless, tooltip "Reset to preset value: <value>". Unchanged rows render the button with visibility: hidden so controls do not shift.
  • Click: write the preset value through the same change path as an edit (store write + effect), then re-render the form. The state must update live while dragging a slider, without re-rendering — recompute after the store write, on the row that fired the event.
  • A gate (the checkbox or select in a section header) gets the same treatment inside the header.

Colour rows

The colour input keeps its swatch; the read-only <output> beside it becomes an editable hex field (5.2em, monospace). Typing a valid #rrggbb and leaving the field writes the value and syncs the swatch; an invalid value reverts to the swatch's value. Dragging the swatch updates the field live.

Everything else

Unchanged: sliders, selects with an inherit option for nullable attrs, number inputs, text inputs with none placeholder, and the custom controls (font picker with +, unit input, blur, transform, label style, percent, scheme, texture, icon, emoji, vignette preset, map filter).

Section cards and previews

Cards are the schema's sections, nothing more. The form renders exactly the <details> tree it renders today; the card is the styling of that tree.

  • Each top-level section (States body, States halo, Coastline bands…) is a card: 1px border in --dark-solid, 5px radius, 10% white fill; header 20% white fill, 0.3em/0.5em padding, bold; body padded 0.2em 0.5em 0.3em 0.9em.
  • Nested sections (a section inside a section, e.g. Anchors under a burg-icon group) are cards inside the card body, 0.3em apart.
  • Rows that belong to no section — a label group, rivers, the map element — get one card titled by the selection: Labels · capital, Rivers.
  • Header contents, left to right: disclosure caret (▸/▾, native <summary> behaviour), section title, gate control if the section has one, change count "n changed" in #7a2e2e when n > 0, and the preview pushed to the right, capped at 50% of the header width.
  • Cards remember open/closed per section id for the session (today's details.open = true default remains).

Previews

A preview reads only the rows inside its own card, from the store, and re-renders on every input/change event of the form. It shows what the card's fields produce, in this order of preference:

Swatch and line may appear together (a section with fill and stroke); text sample replaces both. Previews never trigger a redraw of the map.

The two dialogs

Both are ordinary jQuery UI dialogs appended to #dialogs, opened by the tab's buttons, destroyed on close, positioned by default at the Menu's right edge (my: "left top", at: "right+10 top", of: "#options") and remembered by the existing dialog-position persistence. Neither closes on a pick; both re-render when the selection or the preset changes elsewhere.

Style elements

  • Width 20em, height capped at 70% of the viewport with an internal scroll. Contents: a filter box, then one row per style element in the same alphabetical order as the Element select.
  • Row grid: caret (1em) · visibility dot (1em) · name · count. Rows are 1.9em tall; hover 25% white; the current selection 45% white and bold.
  • The dot is green when the layer is on, hollow when off, grey when the element is permanent or not a layer (map, landmass, fogging). Clicking it toggles the layer through Layers.toggle — exactly what the Layers tab does.
  • Grouped elements (labels, burg icons, routes, lakes) show a caret and the number of groups; clicking the caret expands a nested list, indented under a thin guide, with the same labels and counts the Group select shows ("river … 110"). Clicking a parent selects it with its first group and expands it.
  • The filter matches element names and group names; while filtering, matching grouped elements are shown expanded.
  • A pick calls the editor's open(element, group); the dialog stays, re-renders and highlights the new selection. External opens (Ctrl+click on a layer button, an editor's "edit style" link) update the highlight too.

Style presets

  • Width 36em. A four-column grid of cards: a 16:9 screenshot, the display name beneath it (system names capitalised, custom ones with the [custom] suffix the select already uses). The current preset has a 2px #f5c542 border and a light fill.
  • Clicking a card applies the preset through the same path as the select — including the once-per-session "unsaved style changes will be lost" confirmation — and the dialog stays open with the new current card highlighted.
  • Screenshots are shipped assets: public/images/style-presets/<name>.png, 320 × 180, one per system preset, rendered from the same seed at the same view. A preset without an image (a custom one, or a failed load) shows a neutral tile labelled custom. The +/− (save / remove custom) buttons stay in the tab's preset row.

Behaviour rules

The baseline and what counts as changed

  • The baseline is the parsed JSON of the current preset (options.map.style.preset): the bundled default, a fetched system preset, or a custom one from localStorage run through the legacy upgrader. Load all presets once, lazily, on first open of the tab; the tab renders without change marks until the baseline is ready, then decorates.
  • A path is changed when the preset defines that path and JSON.stringify(store value ?? null) !== JSON.stringify(preset value ?? null). Paths the preset does not define — a label group added after the preset was applied, a burg group the preset never had — are never marked and have no reset.
  • Reset writes the preset's value (including null) through the editor's change, so the attribute is written or removed and the element's effect runs (redraw, refit of state labels, and so on).
  • "Reset element" resets every changed leaf of the current selection in schema order, then re-renders once.
  • After a preset change the baseline switches, every mark disappears (the store now equals the preset), and both dialogs re-render.

Selections that need care

  • Burg icons compose two store records (burgIcons.burgIcons.groups[g] and burgIcons.anchors.groups[g]) into one form with an Anchors subsection. Reset and change detection must map a relative path back to the right record, as storePath does.
  • Gated sections (bands, contours, halos): the gate control lives in the card header and keeps hiding the body when off. A reset of the gate re-renders so the body follows.
  • Grouped elements resolve a missing group to the first one; the Group select, the toolbar and the elements dialog all follow the resolved group.
  • Hidden layers keep the banner above the cards; the banner's "Turn on" re-renders the form.

Rendering discipline

  • Editing never re-renders the form: the store write, the effect, the row's changed state, the card counts, the previews and the changes line all update in place. Only a reset, a selection change or a preset change re-renders.
  • Previews and counts update on the form's bubbled input and change events, after the store write (a microtask/timeout later, as the prototype does).
  • Leaving the tab empties the form and closes both dialogs; opening it again restores the last selection, as today.

Acceptance criteria

  • The Style tab keeps its 330px width, its preset/element/group rows and the schema's section order; every control that exists today still exists and writes the same store path.
  • Each section renders as a card with caret, title, gate (if any), change count and preview; loose rows render in one card titled by the selection.
  • Changing any value marks its row and shows ↺ without re-rendering; ↺ restores the preset's value and runs the element's effect; "Reset element" clears every mark of the selection.
  • The changes line is absent when the selection matches the preset.
  • Colour rows accept a typed hex value; invalid input reverts.
  • Previews follow edits live and never redraw the map.
  • The elements dialog opens beside the Menu, lists every element and group with counts and visibility, filters, toggles layers, selects on click and stays open.
  • The presets dialog shows one screenshot per system preset, highlights the current one, applies on click with the existing confirmation, and stays open.
  • Old maps and legacy custom presets behave as before; a custom preset shows a neutral tile.
  • tsc, biome, vitest (node and browser) and the Playwright attribute-snapshot baselines pass unchanged.

Out of scope and open questions

Not in this iteration

  • Property search across elements and a "Changed only" filter (prototype variants B/E) — the natural next step once reset exists.
  • Scrub numbers replacing sliders (variant C).
  • Any change to the store, the schema, the presets format or the renderers.
  • Mobile layout of the Menu.

Open questions

  • Should "Reset element" ask for confirmation when it touches more than, say, ten values?
  • Thumbnail seed and viewport: one fixed seed for all presets (recommended, so cards compare like for like) — which seed, and should the render zoom in on a region rather than the whole map?
  • Should the elements dialog remember its expanded state between opens?
